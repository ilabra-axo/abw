1. System context and invariants

1.1 Context
ABW is a platform on which agents (versioned configurations run by a bounded tool-calling
LLM loop) make claims about their own work. The target splits the system into two
consistency domains [M §0]:

    The trust domain is event-sourced. It covers:

        claims and their verification;
        gate decisions;
        money;
        agent versions;
        episodes;
        provenance;
        published artifacts (DPP passports).

    History is an append-only event log. Current state is a projection of that log.

    Everything else stays CRUD. That includes UI state, creatures, forecasts' working state,
    workspace files, ontology and memory. These tables are written by ordinary
    transactions under the rules in §14.5.

The trust domain can be cited by the CRUD domain. The reverse is not possible: a trust
record MUST NOT depend on a mutable CRUD row for its meaning. Anything a trust record
refers to is an artifact (content-addressed bytes) or another event.

2.5 Git and object storage
    Workspace git repositories stay libgit2 ( agent-
    bestiary/ontology/src/workspace_git.rs:40-56 [K]).
         Until Phase 3 completes, they stay on a persistent mounted volume under
         GIT_REPOS_PATH . A boot sentinel write and read verifies the volume [M §13.3.3].
         A git commit can never join a Postgres transaction. Every git write that a trust
         record depends on is therefore an outbox job, emitted in the transaction that
         decides it.
         A trust record never depends on git state that could still change. A DPP release
         stores source_commit and the artifact SHAs of every file it read (§10.2).
    Object storage (S3-compatible) holds artifacts over ARTIFACT_INLINE_MAX (256 KiB) [M
    R3.2].
        The upload precedes the referencing transaction.
        The key is the SHA, so an upload is idempotent.
        An orphaned object (uploaded, then the transaction rolled back) is harmless and is
        garbage-collected after 7 days by a worker that checks ledger.artifacts .

3. The ledger crate ( abw-ledger )
abw-ledger (path crates/abw-ledger ) is the write boundary (T1) and the event store (T2).
It owns:

    the only write-capable connection pool;
    the append algorithm;
    inline projections;
    the transactional outbox;
    JCS and hashing;
    the migration runner;
    the crud write module for the non-trust domain.

It depends on sqlx , serde_json , sha2 and an RFC 8785 implementation [P OD-03]. It
does not depend on the root fermi crate. Domain crates depend on it, not the other way
round (§3.9).


3.1 DDL
All DDL below was executed against PostgreSQL 18.6 as written, and the negative cases
were exercised under each role. The record is in Appendix D. Production targets Postgres
16 (LLD §1.1); nothing below needs a feature newer than 13 ( xid8 , pg_current_xact_id ).


3.1.1 Immutability primitive

  CREATE FUNCTION ledger.forbid_mutation() RETURNS trigger LANGUAGE plpgsql AS $$
  BEGIN
    RAISE EXCEPTION 'ABW-T6: % on %.% is forbidden (append-only)', TG_OP,
  TG_TABLE_SCHEMA, TG_TABLE_NAME
      USING ERRCODE = 'insufficient_privilege';
  END $$;


The trigger fires for every role, including the table owner, so it is the second layer behind
grants. Grants stop abw_app ; the trigger stops abw_owner and anything with ownership.
Superuser can still ALTER TABLE … DISABLE TRIGGER . That is an operator action outside the
threat model, and it is detected by the nightly hash-chain audit (§3.10).

3.1.2 stream_kinds and streams
CREATE TABLE ledger.stream_kinds (
  kind         text PRIMARY KEY CHECK (kind ~ '^[a-z][a-z_]{1,31}$'),
  concurrency text NOT NULL CHECK (concurrency IN ('exact','commutative')),
  description text NOT NULL);

CREATE TABLE ledger.streams (
  stream_id text PRIMARY KEY COLLATE "C"
              CHECK (stream_id ~ '^[a-z][a-z_]{1,31}:[A-Za-z0-9._@-]{1,128}$'),
  kind        text NOT NULL REFERENCES ledger.stream_kinds ON DELETE RESTRICT,
  tenant_id text NOT NULL,
  head        bigint NOT NULL CHECK (head >= 0),
  created_at timestamptz NOT NULL DEFAULT now(),
  CHECK (split_part(stream_id, ':', 1) = kind));

-- head may only move forward; identity columns never change; rows are never deleted

-- gap-free: at COMMIT, every advance of head is matched by exactly that many events
CREATE FUNCTION ledger.streams_gap_free() RETURNS trigger LANGUAGE plpgsql AS $$
DECLARE lo bigint := CASE WHEN TG_OP = 'INSERT' THEN 0 ELSE OLD.head END; n bigint;
BEGIN
  SELECT count(*) INTO n FROM ledger.events
   WHERE stream_id = NEW.stream_id AND seq > lo AND seq <= NEW.head;
  IF n <> NEW.head - lo THEN
    RAISE EXCEPTION 'ABW-T2: stream % advanced % -> % but % events were written',
NEW.stream_id, lo, NEW.head, n;
  END IF;
  RETURN NULL;
END $$;

Physical notes:

    Row width. payload is jsonb , TOASTed above about 2 KiB. Payloads MUST stay
    under 64 KiB [P OD-05]. Anything larger is an artifact referenced by SHA. Typical events
    are 300 B – 4 KiB.
    Two orders. global_pos is an identity value. It is allocated at INSERT time, not
    commit time, so it is not a commit order. That is why async readers use (txid,
    global_pos) and a snapshot fence, never global_pos alone (§3.5).
    The one order Rust cares about is the per-stream seq . It is gap-free (enforced by
     t_streams_gap_free at commit) and dense.
     payload_sha is sha256: over the JCS bytes of the envelope-independent payload (§3.6).
     abw-ledger computes it. The database cannot recompute JCS, so the nightly audit re-
    derives it in Rust.
    No jsonb round-trip is trusted for hashing. jsonb normalises numbers and
    reorders keys (validated: {"b":1,"a":[1.0,"x"]} reads back as {"a": [1.0, "x"],
    "b": 1} ). The hash is therefore computed from the Rust value before serialisation into
     jsonb , and re-verification canonicalises the decoded jsonb value. JCS output is
    invariant under both transformations: key order is re-sorted, and 1.0 canonicalises to
     1 either way.

3.2 The append algorithm
Isolation level: READ COMMITTED for command transactions, with explicit row locks [P OD-
06]. Here is why:

    The compare-and-swap ( UPDATE … WHERE head = $expected ) is a guarded single-row
    update. Under READ COMMITTED , a concurrent writer blocks on the row lock. When it
    wakes, Postgres re-evaluates the WHERE against the new row version (EvalPlanQual).
    The loser sees head ≠ expected and updates 0 rows: a clean, typed conflict with no
    serialisation error.
    Under REPEATABLE READ the loser gets SQLSTATE 40001 instead (validated, Appendix
    D case 20). That is also correct, but it is indistinguishable from other serialisation
    failures.
    Reads that a decision depends on are protected by locks, not by isolation level: the
    aggregate fold, the cited stream heads, and the wallet balance. abw-ledger takes FOR
    SHARE on every stream it reads for a decision and FOR NO KEY UPDATE on every stream
    it appends to, in one ordered pass (§3.2.2).

3.2.2 Lock order and deadlock freedom
    Rule L1. Within one transaction, stream rows are locked once, in ascending stream_id
    COLLATE "C" order, by lock_streams , before any other row lock.
    Rule L2. Projection rows are locked only after L1, and only through their own stream. A
    projection row is keyed 1:1 by its stream, for example proj.wallets.stream_id
    UNIQUE , proj.claims.stream_id UNIQUE . Holding the stream lock therefore serialises
    writers of that projection row.
    Rule L3. Unique-index entries (artifacts, command_dedup , events_money_idem ) may be
    contended. Their waits are bounded: the conflicting transaction is either committing or
    aborting, and it never waits on a stream lock the current transaction holds. That is
    because L1 is complete before step 7.

A wait-for cycle needs two transactions that each hold a lock the other wants. Under L1,
every stream lock is acquired in one global order, and by L2 and L3 nothing acquired later
waits on a stream lock. So no cycle exists. Money transfers lock the two wallets in
 stream_id order. That is the same rule SPEC 36 states as "uuid order" [M R1.1]: both
 wallet: IDs share a prefix, so bytewise order on the stream ID equals bytewise order on
the UUID's text form.

3.5 Read-side visibility for asynchronous consumers
The problem. global_pos is assigned at insert, but transactions commit in a different
order. A reader that checkpoints on global_pos alone permanently skips any event whose
transaction was still open at read time with a lower global_pos .

SPEC 36's fence is insufficient. SPEC 36 R2.6 checkpoints on global_pos and filters txid
< pg_snapshot_xmin(pg_current_snapshot()) . That still skips events, because xid order is
not global_pos order either. A transaction can take its xid early (for example, by locking a
stream row) and insert its event late, while a later-xid transaction inserts first. This was
reproduced (Appendix D case 26):


   stream_id | global_pos | txid
   episode:H |          9 | 1075       <- later xid, lower position, committed second
   episode:L |         10 | 1073       <- earlier xid, higher position, committed first


The sequence of events in that run:

  1. With a third transaction (xid 1074) open, the fence admitted L (1073 < 1074). The
     checkpoint advanced to global_pos = 10 .
  2. When 1074 closed, H (pos 9) became visible.
  3. global_pos > 10 never returns H , so H was lost.

Target fence. The checkpoint is the pair (fence_txid, fence_pos) , and events are
consumed in (txid, global_pos) order, below the snapshot's xmin :


  -- run in its own READ COMMITTED transaction by the async projector
  SELECT global_pos, stream_id, seq, event_type, schema_version, payload, txid
    FROM ledger.events
   WHERE (txid, global_pos) > ($fence_txid::xid8, $fence_pos::bigint)
     AND txid < pg_snapshot_xmin(pg_current_snapshot())
   ORDER BY txid, global_pos
   LIMIT $batch;                                    -- uses index events_fence (txid,
  global_pos)


Why it is complete:
    Every transaction with xid < xmin has finished; that is the definition of xmin . So the
    set of events with txid < xmin is closed: no new row can ever join it.
    Ordering by (txid, global_pos) and checkpointing the last (txid, global_pos)
    consumed therefore never skips a committed row.
    Rows from aborted transactions never become visible and are simply absent.
    Applied to the validated scenario, the target fence returns H on the second round
    (Appendix D case 27).

Cost and liveness.

    The query is a range scan on events_fence . The plan is a bitmap index scan on
     ROW(txid, global_pos) > ROW(…) with txid < xmin as an index condition.
    Lag is bounded by the oldest open transaction in the cluster.
     idle_in_transaction_session_timeout = 30s on abw_app bounds it to 30 s for ledger
    transactions. A long abw_read report holds xmin too, so abw_read sessions carry
     statement_timeout = 60s . Projector lag is exported as now() − recorded_at of the
    last consumed event, with an alert above 60 s.
    Checkpoint atomicity. Each batch's projection writes and the checkpoint UPDATE
    commit in one transaction, so a crash re-delivers at most one batch. Async projectors
    MUST be idempotent per (global_pos) ; each async projection row records the
     global_pos it last applied.
    Leases. Each projector holds a lease ( lease_owner , lease_until , refreshed every
     TTL/3 ), so two workers never run the same projector. This replaces the consolidation
    lease pattern whose extend had no caller (G28).

Inline readers need no fence. An inline projection is written in the same transaction as its
event, so ordinary MVCC visibility makes event and projection appear together.


3.6 JCS canonicalisation and the hash format

3.6.1 Byte rules
The canonical form of a JSON value is RFC 8785 (JCS). An implementation MUST follow these
rules, which restate RFC 8785 §3.2 in implementable terms:

  1. Input domain is I-JSON (RFC 7493).
         Strings MUST be valid Unicode: no lone surrogates.
        Numbers MUST be IEEE-754 binary64 values. An integer outside ±(2^53 − 1) is
        rejected, not rounded.
        Object member names MUST be unique; duplicates are rejected at parse.
         NaN and ±Infinity are rejected.
  2. Whitespace. None is emitted.
  3. Literals are null , true and false .
  4. Strings.
          Output as UTF-8, enclosed in " .
        Escaped as exactly \" , \\ , \b , \f , \n , \r and \t .
        All other code points below U+0020 are written \u00xx with lowercase hex.
        Everything else, including / , DEL and all non-ASCII, is emitted raw.
  5. Numbers use the ECMAScript Number.prototype.toString algorithm (ECMA-262
     §7.1.12.1). Let the shortest round-trip digit string be d ( k digits) and the decimal
     exponent n , with value = 0. d × 10^n:
          -0 is written 0 .
        If k ≤ n ≤ 21 , write d followed by n − k zeros. Examples: 100 ,
         100000000000000000000 .
        If 0 < n ≤ 21 , write d[0..n] . d[n..] . Example: 4.5 .
        If −6 < n ≤ 0 , write 0. then −n zeros then d . Example: 0.000001 .
        Otherwise use exponent form: d[0] , then .d[1..] if k > 1 , then e , the sign
        ( + or - ), and |n − 1| . Examples: 1e+21 , 5e-7 , 1e-27 .
  6. Objects. Members are sorted by their names compared as sequences of UTF-16 code
     units, not code points or UTF-8 bytes. This differs from code-point order for characters
     above U+FFFF. Values are canonicalised recursively.
  7. Arrays keep their order. Elements are canonicalised recursively.
  8. Hash. sha256: ‖ lowercase hex of SHA-256 over the UTF-8 bytes of the canonical text:
     71 ASCII characters in total, matching ^sha256:[0-9a-f]{64}$ .

For raw-utf8 artifacts the hash is over the UTF-8 bytes as given, with no normalisation,
and for raw-bytes it is over the bytes as given. The canonicalisation tag is stored with the
artifact, so a verifier knows which rule to apply.

This replaces artifact_hash::canonical ( src/artifact_hash.rs:118-133 [K: to be
replaced]). That function sorts keys bytewise and emits serde_json compact output, which
is not JCS. The two disagree on:

    floats, because serde_json emits 1e30 where JCS emits 1e+30 ;
    key order above U+FFFF.

Every hash computed by the old function is recomputed in migration, with legacy_sha
kept for one release [M R3.1].

Rust implementation constraint. The root crate enables serde_json/preserve_order
( Cargo.toml:61 [K]). JCS MUST NOT depend on map iteration order; it sorts explicitly. It
MUST also NOT go through serde_json 's float formatter, which is ryu shortest but
formatted differently; it MUST format with the ECMAScript algorithm above.

3.6.3 Floats in trust payloads
A verdict MUST be reproducible bit for bit (T11), so every score, θ and probability in a trust
event is encoded as integers:

      Fractions are (num, den) pairs. For example, Truth is matched/total as score_num
      and score_den .
      Thresholds are basis points ( theta_bp , 0–10000).
      Probabilities are parts per million ( p_ppm , 0–1000000).
      Brier scores are millionths ( brier_micro ).

Comparisons are exact integer arithmetic: score_num × 10000 ≥ theta_bp × score_den .
This avoids any dependence on float formatting, platform rounding or jsonb 's numeric
normalisation [P OD-07]. The Lattice spec's JSON example uses decimals
( "score":0.81,"theta":0.70 ) [S §Event schema]. The API read model renders decimals for
display, computed from the stored integers.

3.9 How the type system makes direct writes impossible
T1 requires that "a handler that tries to write directly fails to compile" [R §5 Phase 1
acceptance]. The mechanism has four layers. Each layer closes a hole the previous one
leaves open.

  1. No write pool is nameable outside the crate.
         Ledger 's pool field is private.
         AppState holds ledger: Arc<Ledger> and db: ReadDb , and no PgPool field.
        The current db: PgPool ( src/api_server.rs:433 [K: removed]) is replaced, so
        handler code that passes &state.db to sqlx::query(..).execute(..) with a
        write statement no longer has a write-capable executor to pass.
  2. ReadDb is not a write executor.
         ReadDb::as_executor returns a pool connected as abw_read . Strictly, sqlx
        would still compile an UPDATE against it; the database refuses it at run time
        ( cannot execute INSERT in a read-only transaction , and grants deny it even
        under BEGIN READ WRITE : Appendix D cases 12, 13, 18).
        To reach compile time as well, ReadDb exposes only fetch_one , fetch_optional
        and fetch_all , each taking a ReadQuery .
         ReadQuery is built only by the read_query! macro. The macro parses the SQL
        literal at compile time and emits compile_error! unless the first keyword is
         SELECT or WITH , it contains no data-modifying CTE
         ( INSERT|UPDATE|DELETE|MERGE ), and it contains no FOR UPDATE or FOR SHARE [P
         OD-09].
  3. The crate graph forbids the bypass.
         Handler and executor crates do not depend on sqlx with the postgres feature
         directly. They see sqlx types only through abw-ledger 's re-exports, which include
         no PgPool::connect .
         Concretely, the root fermi crate's handlers move to a fermi-http crate whose
          Cargo.toml has no sqlx dependency. cargo deny with a bans entry prevents
         adding one [P OD-10].
         A test in tests/claims/no_write_pool.rs fails if any crate other than abw-ledger
         and the explicitly listed CRUD-free utility binaries calls PgPoolOptions::connect* .
  4. Commands are the only path to ProjTx .
         ProjTx<'t> has a private constructor and a lifetime tied to the dispatch
        transaction.
         Inline projectors receive &mut ProjTx . They cannot store it, return it, or open their
         own transaction.
          Tx is deliberately !Send (it holds a PhantomData<*const ()> ). No future that
         holds a ledger transaction across an .await on a non-ledger future can be
         spawned onto the multi-thread runtime, so "LLM call inside a transaction" is a
         compile error at the tokio::spawn boundary. The only .await s inside dispatch
         are ledger-internal.

5.3 Dependencies
Dependencies are declared in one table in abw-lattice::evaluate , applied after every
dimension's raw result is computed. This preserves "lattice, not ladder" [S P2]:


  pub const DEPENDENCIES: &[Dependency] = &[
      // "Truth requires Presence. With no artifact there is nothing to diff, so Truth
  is not evaluated."
      Dependency { dim: Truth, on: Presence, when_on: NotPass, becomes: NotEvaluated,
  class: "presence_failed" },
      // "If Truth passes and Grounding fails, Truth is unsupported"
      Dependency { dim: Truth, on: Grounding, when_on: Fail, becomes_if_pass:
  Unsupported, class: "grounding_failed" },
  ];
  // Liveness and Binding: independent.


The evaluation order is:

  1. Compute all five raw results.
  2. Apply the Presence→Truth rule.
  3. Apply the Grounding→Truth rule, which only changes a pass to unsupported .

The raw Truth score is kept even when Truth is unsupported or not_evaluated . In the
 not_evaluated case it is null , because no diff could run. Routing and the outer loop can
therefore see the dimension's own result. This is also what the spec's example shows:
 {"dim":"truth","state":"unsupported","score":0.81,"theta":0.70} [S §Event schema].
5.4 Verdict states

  pub enum DimState { Pass, Fail, Unsupported, NotEvaluated }          // closed: T12


There is no other state. In particular:

    there is no Undetermined in the vector (that is gate vocabulary, §8);
    there is no Skipped ;
    there is no Error .

An infrastructure error while loading inputs (an object store timeout, a walk that exceeds
its statement timeout) is not a verdict. The evaluation transaction aborts and the job
retries. After max_attempts , the claim receives lattice.evaluated with the affected
dimension not_evaluated and class infra_unavailable . That evaluation is marked
 infra_degraded: true , which routing treats as not-pass (§5.10).

T12 is enforced in three places:

    the type (a four-variant enum);
    the event JSON Schema ( "enum": ["pass","fail","unsupported","not_evaluated"] );
    the conformance test lattice_missing_substrate_never_passes (§15).

The reproducibility contract (T11):

  1. abw-lattice::inputs::load reads every input in one REPEATABLE READ transaction
    (TX-D), so the inputs form one consistent snapshot. All reads are through the same
    transaction that later appends (§5.11).

  2. inputs_sha = sha256_jcs(LatticeInputs) is stored in lattice.evaluated , and the
    full LatticeInputs is stored as an artifact ( media_type =
    application/vnd.abw.lattice-inputs+json ) referenced by inputs_sha .

  3. Replay ( GET /api/claims/:cid/replay , [M R7.12]) loads the inputs artifact by SHA and
     the policy document by (policy_id, version) , verifies doc_sha , runs evaluate , and
     asserts sha256_jcs(vector) == lattice.evaluated.payload_sha . Identity of the
     payload hash is the bit-for-bit criterion.

  4. Re-derivation ( ?mode=rederive ) re-runs inputs::load as of the original evaluation
     and compares the result with the stored inputs:

        Stream heads are taken from ledger.events with global_pos ≤ the
        evaluation's own global_pos .
        Provenance is taken from prov.edges with event_pos ≤ prov_high_water .

    Because events, artifacts and edges are immutable (T6), re-derivation reproduces the
    inputs. A mismatch proves a defect in load . This is the stronger form of the directive's
    acceptance test "Replay: the verdict vector is reproduced exactly from (claim, artifacts,
    stream heads, provenance graph, θ version)" [R §5 Phase 2].

5.8 Residual risk
"A fully passing vector carries a per-dimension false-pass rate, not a guarantee" [S P5].

    Population. Residual risk is computed by the outer-loop projection (§11.1) for each
     (dimension, policy_id, stakes_class) , over claims where that dimension was pass
    and an outcome or a human decision later established truth.

    Formula. It is the Beta posterior mean with a Beta(1,1) prior:

         false_pass = false_pass_count + 1 ;
         denominator = checked_pass_count + 2 .

    It is stored as a ratio. With fewer than 30 checked passes it is labelled prior_only:
    true [M R7.4].

    Reproducibility. The value in a vector is read from the read model as of the evaluation
    transaction's snapshot and copied into LatticeInputs . It is therefore reproducible
    without recomputing the read model.

Async read models. The read models named here and in §11.1 ( proj.loop_inner ,
proj.calibration , proj.loop_outer ) are given as column lists, not DDL.

    They are async projections: rebuildable, and written only by their projector through
     ProjTx with a checkpoint (§3.5).
    Each row is keyed by its grouping columns plus applied_pos .
    No trust decision reads them, except through a value copied into LatticeInputs .

The judge is mandatory, and its output is interpretive [S §Judge].

Independence rules:

 1. Model family.
       Families are declared data in the lattice policy ( judge_policy.families ):
        anthropic-claude , openai-gpt , mistral , qwen , glm , … [M R7.6].
       The judge for a claim MUST be from a different family than
        claim.proposer_model.family . That family is taken from
        episode.opened.model_family , which records what actually ran, not the card's
       declared model.
       The current judge default, claude-haiku-4-5-20251001
       ( src/handlers/eval_judge.rs:37 [K: to be replaced]), is the same string as the
       default agent model, so the current default fails this rule.
 2. Prompt lineage.
        prompt_lineage is an ID declared in abw-judge , and prompt_sha hashes the full
       system prompt.
       The lineage MUST NOT be derived from any proposer card: the judge prompt is
       not built from the proposer's system_prompt , and prompt_sha ∉ {card
       prompt_sha of the proposer} .
        Both conditions are checked in judge.report command decide [M §15].
 3. Injection-safe delimiting.
        The task, claim and artifact enter the prompt only as JSON string values
        ( serde_json escaping) inside a block delimited by <<ABW-DATA-{nonce}>> …
         <<END-ABW-DATA-{nonce}>> , where nonce is 128 bits from OsRng , generated per
        call.
        The system prompt says that content inside the block is untrusted data and that
        instructions inside it are to be reported as findings, not followed.
        A payload containing the nonce string is impossible by construction: the nonce is
        generated after the payload is fixed, and a collision is checked and regenerated.
        The current direct interpolation AGENT OUTPUT:\n{} ( eval_judge.rs:99 [K: to be
        replaced]) is removed [R §4 G12].
           nonce_sha (not the nonce) is stored, so the prompt is reproducible from stored
          parts given the nonce, which is kept in the report artifact.
  4. Unavailable judge. If no independent judge is configured or reachable within
      JUDGE_TIMEOUT (60 s) after max_attempts (3), the worker appends judge.unavailable
     { cid, attempt, reason_class: infra_error|insufficient_input } . Routing treats
     this as a block intent finding with confidence_ppm = 0 , so the claim goes to a human
     rather than Proceed [M R7.6].
  5. No certifying authority. evaluate() has no parameter of any judge type (§5 module
     table). Nothing in the report can raise a dimension.

Measured reliability. The middle loop scores findings against outcomes (§11.1). The
subject of calibration.updated is judge:<family>/<model>@<prompt_lineage> .

Injection test. tests/claims/judge_injection.rs runs a fixed corpus of injection payloads
with a fixed seed. It asserts that the finding severity flip rate relative to a clean control is at
most the threshold in OD-14 [M §16.6].

5.11 Transaction boundaries
TX-D is the claim evaluation transaction: a REPEATABLE READ dispatch of claim.evaluate ,
run by the claim.evaluate outbox worker.

  1. BEGIN ISOLATION LEVEL REPEATABLE READ .
  2. lock_streams(W = {claim:<cid>}, R = {episode:<eid>} ∪ cited streams) .
  3. inputs::load : every read of §5.2, in this snapshot.
  4. Check that judge.reported or judge.unavailable exists for (cid, attempt) . If it
     does not, ROLLBACK ; the judge job will re-enqueue claim.evaluate when it finishes.
  5. evaluate (pure), then route (pure).
  6. Append lattice.evaluated , route.decided , and the consequence events. Store the
     LatticeInputs artifact and the packet artifact if routing chose Endorse or SignOff.
  7. Inline projection proj.claims .
  8. Outbox jobs: claim.correct (re-invoke the agent), notify.assignee , notify.owner .
  9. COMMIT .

Why REPEATABLE READ here (and READ COMMITTED for other commands):

    The inputs span several tables. Liveness compares a cited seq with heads that may
    move during the load. A single snapshot makes the inputs self-consistent, so replay
    reproduces them.
    The streams in R are share-locked, so a conflicting append to a cited stream waits
    until TX-D commits. The vector cannot be invalidated between load and commit.
    An append to an uncited stream is irrelevant by definition.

Judge before lattice. The judge runs outside any transaction (an LLM call; §2.3). It writes
 judge.reported in its own short transaction on claim:<cid> and then enqueues
 claim.evaluate . The lattice evaluation needs no LLM, so placing it after the judge costs
nothing and satisfies "routing waits for both".

Inline fast path. When the judge is fast (≤ ROUTE_WAIT_MS ), the request handler MAY run
the judge itself after TX-C and dispatch claim.evaluate directly. The transaction shape is
identical.

Why this makes an interpretive node unreachable in any Grounding walk (T10).

  1. The walk (§6.5) starts at an evidentiary artifact: the claim's subject artifact. It follows
     only quotedFrom , wasDerivedFrom and hadPrimarySource edges with
      object_epistemic = 'evidentiary' .
  2. That filter alone suffices, but the database guarantees more, so a buggy walk cannot
     leak either:
         By (a), no edge whose relation is walkable has an interpretive object.
         By (b), no evidentiary node has any edge into an interpretive node except
          wasInformedBy , wasAttributedTo and wasAssociatedWith , none of which a
         source walk follows.
  3. By induction over path length, every node reachable from an evidentiary start by
     walkable edges is evidentiary.
  4. The composite FKs mean an edge cannot lie about an endpoint's class. Node classes
     are immutable ( t_nodes_immutable ), so a node cannot be reclassified after the fact.

The judge's own subgraph is allowed:

     artifact:<report> --wasGeneratedBy--> judge:<cid>/<attempt> is interpretive to
    interpretive.
     judge:… --used--> artifact:<enforced> is interpretive to evidentiary, which is
    permitted.

It is a dead end in the evidentiary direction. A query that starts from the claim can find the
report only through edges_reverse ( object = artifact:<enforced> , relation = used ),
and that is how the packet assembles the report for humans. ΞPROV therefore records that
the report exists and where it came from (model, prompt version, inputs), exactly as the
spec requires [S §Judge].

The four rejection cases were validated (Appendix D cases 30–33):

    a judge report as quotedFrom source;
    a mislabelled object class;
    an evidentiary artifact wasGeneratedBy a judge;
    an episode that used a judge report.
The last two matter: they stop an agent from consuming a judge report as input and
laundering it into evidence.

Claims can never cite a judge report as evidence. claim.submit rejects any
artifact_refs or tool_call_refs element whose artifact has a prov.nodes row with

6.5 The chain walk
The walk runs in TX-D through the transaction's connection, against the snapshot. It
returns every reachable row up to the depth bound, with cycle marking. The fold into an
 Origin is done in Rust ( abw-lattice::inputs ), because wasDerivedFrom at field level is
all-of (a derived value is only as grounded as its weakest input) while quotedFrom and
 hadPrimarySource are any-of.


  -- origin_of($1 = start node, $2 = JSON pointer in start node, $3 = depth bound,
  default 16)
  WITH RECURSIVE walk(node, path, depth, parent_edge, visited, is_cycle) AS (
      SELECT $1::text COLLATE "C", $2::text, 0, NULL::bigint,
              ARRAY[($1::text || '#' || $2::text) COLLATE "C"], false
    UNION ALL
      SELECT e.object,
              CASE WHEN e.relation = 'hadPrimarySource' THEN '' ELSE e.object_path END,
              w.depth + 1, e.edge_id,
              w.visited || (e.object || '#' || e.object_path),
              (e.object || '#' || e.object_path) = ANY (w.visited)
        FROM walk w
        JOIN prov.edges e
          ON e.subject = w.node
         AND e.object_epistemic = 'evidentiary'
         AND ( (e.relation IN ('quotedFrom','wasDerivedFrom') AND e.field_path =
  w.path AND w.path <> '')
               OR (e.relation = 'hadPrimarySource' AND e.field_path IN ('', w.path)))
       WHERE NOT w.is_cycle
         AND w.depth < $3
         AND NOT EXISTS (SELECT 1 FROM prov.nodes t
                           WHERE t.node_id = w.node AND t.origin_kind IN
  ('external','human_attested'))
  )
  SELECT w.depth, w.node, w.path, w.parent_edge, n.origin_kind, w.is_cycle,
         NOT EXISTS (SELECT 1 FROM walk c
                       WHERE c.depth = w.depth + 1 AND c.visited[1:w.depth+1] =
  w.visited) AS frontier
    FROM walk w JOIN prov.nodes n ON n.node_id = w.node
   ORDER BY w.depth, w.parent_edge;

Cost.

    Each recursion step is an index lookup on edges_walk (subject, field_path,
    relation) , with the object columns in INCLUDE , so the edge table needs no heap
    fetch. Run-written chains are 2–4 hops, so a typical field costs 3–5 index probes.
    Worst case is O(b^D) rows for fan-out b. statement_timeout = 2s on the walk
    bounds it in time, and exceeding the timeout is infra_unavailable , not pass (T12).
    A batched form seeds the CTE with all fields of the claim ( unnest($pointers) ) so one
    round trip serves every field. On the validation fixture's small tables the planner chose
    bitmap scans. At production cardinalities edges_walk is expected to drive a nested
    loop; EXPLAIN belongs in the Phase 2 performance test (§15,
     prov_walk_plan_uses_index ).

-- per-stream chain: balance_after(seq) = balance_after(seq-1) + delta
CREATE FUNCTION ledger.wallet_chain_check() RETURNS trigger LANGUAGE plpgsql AS $$
DECLARE prev_after bigint; d bigint; after bigint;
BEGIN
  IF split_part(NEW.stream_id, ':', 1) <> 'wallet' THEN RETURN NEW; END IF;
  d     := (NEW.payload->>'delta')::bigint;
  after := (NEW.payload->>'balance_after')::bigint;
  IF d IS NULL OR after IS NULL THEN
    RAISE EXCEPTION 'ABW-T9: wallet event % lacks delta/balance_after',
NEW.event_type;
  END IF;
  IF NEW.seq = 1 THEN prev_after := 0;
  ELSE
    SELECT (payload->>'balance_after')::bigint INTO prev_after
      FROM ledger.events WHERE stream_id = NEW.stream_id AND seq = NEW.seq - 1;
    IF NOT FOUND THEN RAISE EXCEPTION 'ABW-T2: wallet % seq % has no predecessor',
NEW.stream_id, NEW.seq; END IF;
  END IF;
  IF prev_after + d <> after THEN
    RAISE EXCEPTION 'ABW-T9: wallet % chain broken at seq %: % + % <> %',
NEW.stream_id, NEW.seq, prev_after, d, after;
  END IF;
  RETURN NEW;
END $$;
CREATE TRIGGER t_events_wallet_chain BEFORE INSERT ON ledger.events
  FOR EACH ROW EXECUTE FUNCTION ledger.wallet_chain_check();

-- double entry: per transaction, wallet deltas sum to zero; checked at COMMIT

BEGIN

    FROM ledger.events WHERE txid = NEW.txid AND stream_id LIKE 'wallet:%';
  IF s <> 0 THEN

NEW.txid, s;
  END IF;
  RETURN NULL;
END $$;

Why the balance can never drift from the ledger.

 1. abw_app has no UPDATE on proj.wallets (Appendix D case 5). The only writer is
    apply_wallet_event , a SECURITY DEFINER trigger fired by the event insert.
 2. The trigger applies exactly the event's deltas, guarded by applied_seq = seq − 1 , so
    out-of-order application is impossible.
 3. wallet_chain_check makes balance_after a running sum of delta over the stream
   (case 7). The fold of the stream therefore is balance_after at head.
 4. wallet_matches_head re-checks the equality at commit (T3).
  5. CHECK (held <= balance) and granted, purchased ≥ 0 reject an overdraw at the
    statement that would cause it (case 9). There is no time-of-check/time-of-use gap,
    because the wallet stream row is locked for the whole transaction (L1).
  6. Even abw_owner cannot change the projection without an event (case 6, the T3 guard).

The current balance is read from proj.wallets ( O(1) ). The ledger identity balance = Σ
delta is a nightly audit query and a conformance test, not a runtime cost.

Reliability posterior (middle loop). The posterior for a subject is Beta(a, b) :

     a counts outcomes where the subject's forecast or endorsement held;
     b counts those where it did not.

It starts at Beta(1, 1) . Brier is the mean of per-claim (p − o)² . Human endorsers are in
the middle loop: an endorsement is scored as a forecast that the claim will hold, with p =
1 unless the endorser supplied a confidence [S §Loops].

claim will fail, with p = confidence_ppm .

13.1 Tenancy
T17 states the rule: a read by opaque ID returns 404 unless the caller is authorised. It is
404, not 403, because 403 would be an existence oracle [R §4 G02] [M R0.2].

    Where the tenant lives. Every trust stream has streams.tenant_id , and every inline
    projection carries tenant_id .
    Authorisation function. Authorisation is one function per object kind:
     authorize_read(principal, kind, id) -> Result<(), NotFound> in fermi-
    http::authz . It reuses fermi_auth::visibility ( fermi-auth/src/lib.rs:13 [K]) for
    sharing rules. It is applied by an Axum extractor ( Authorized<Kind> ) that resolves the
    path ID, so a handler cannot receive an ID it has not authorised.
    Coverage. tests/claims/idor_matrix.rs enumerates every GET route with a :…id
    parameter from the route table (the existing parser at tests/route_table.rs:31-40
    [K]). For each one it asserts that a second user gets 404, with zero exemptions unless a
    written reason is in the test.

     /api/claims/:cid/replay ) are tenant-scoped by the node's tenant_id . Public DPP

    The public flag exposes only the manifest, the snapshot and the claims the manifest
    lists.

14.5 CRUD-domain rules
The CRUD domain keeps mutable tables. T1 still holds: CRUD writes go through
 abw_ledger::crud , which is the only holder of a connection able to SET LOCAL ROLE
abw_crud .

    Mixed transactions. A command that writes both trust and CRUD state does so in one
    transaction. For example, app.spawn writes public.teams and the wallet transfer.
        The command runs SET LOCAL ROLE abw_crud for the CRUD statements and
         RESET ROLE before ledger statements.
        The roles are disjoint: abw_crud cannot touch ledger.* , and abw_app cannot
        write public.* . A statement in the wrong role fails (validated, Appendix D cases
        38–40).
    Rules for CRUD writes:
        no let _ = on a write [R rule 2];
        two writes that must agree go in one transaction;
        optimistic concurrency ( WHERE version = $v ) on any row the UI edits
        concurrently.
    API. Crud::tx(&self) -> CrudTx exposes a typed query builder plus execute_crud!
    ("…") . The macro refuses at compile time to name any table in the ledger , prov or
     proj schemas, or any table listed in TRUST_TABLES [P OD-35].
